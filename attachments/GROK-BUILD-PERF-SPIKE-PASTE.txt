ROOT CAUSE (fix this — do not hand-wave)
Every successful entity PATCH calls publishEntityWrite → invalidateCompanyWire() which nulls wireCache AND wireInflight.
Then N concurrent GET /api/company each miss cache and run full loadCompanySnapshot + overlay/assembleForGet + JSON.stringify + gzipSync (~5.8MB).
Invalidating mid-flight cancels single-flight coalescing → rebuild stampede under 10 writers+readers.
That is the lag. Idle INM is fine; concurrent write+read is not.

### Fix 1 — Stale-while-revalidate wire (stops the spike)
Change invalidateCompanyWire behavior for hot entity writes (people / reward-records / month-records / target-cells):

1. Keep serving the **previous** wireCache to GET /api/company while a rebuild is in flight.
   - Do NOT set wireCache = null on every entity PATCH.
   - Do NOT cancel an in-flight rebuild by nulling wireInflight mid-flight.
2. Mark the cache dirty (bump a dirtyGen / needsRebuild flag). Coalesce: at most **one** rebuild runs; if more writes arrive during rebuild, run **one** more rebuild after it finishes (never N parallel assembles).
3. When rebuild completes, atomically swap wireCache + etag/at/bookGens.
4. Readers that already have the new etag get unchanged:true; readers with old etag get the new wire once — still one assemble for the whole fleet, not one per request.

Acceptance: under a test that does 10 parallel entity PATCHes + 20 parallel GET /api/company, max GET TTFB stays **< 2.0s** and there is **≤ 2** full assemble/gzip builds (not 20).

### Fix 2 — Patch-in-place for single-entity writes (preferred when cache warm)
When wireCache is warm and the write is a single entity PATCH:

- People: merge that one person into slim.people (or soft-delete), bump notebookUpdatedAt / org bookGen, re-stringify + gzip **from the patched slim** — skip full assembleForGet / loadCompanySnapshot.
- Reward-records / month-records: merge that one period+personId cell into the slim maps the same way; bump months gen.
- Target-cells: same for targets.
- Fall back to full rebuild only if cache is cold, slim missing that collection, or restore/admin paths.

Acceptance: after a people PATCH with warm cache, GET /api/company does not re-query all hot tables; unit test proves assembleForGet was NOT called (spy) for that path.

### Fix 3 — publishEntityWrite must not stampede
In company-live.ts publishEntityWrite:
- Still bump live at + bookGens + entities[] for SSE/tick (needed for live).
- Call a new softInvalidateCompanyWire() / scheduleWireRebuild() from Fix 1 — **not** the hard nulling invalidate used today on every entity write.
- Hard invalidateCompanyWire() only for restore, book-wide PATCH, admin wipe, or cold start.

### Fix 4 — Cold GET still too slow (1.5s → target ≤ 0.5s on Contabo-class)
